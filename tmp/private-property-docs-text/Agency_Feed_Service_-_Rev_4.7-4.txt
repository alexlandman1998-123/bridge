1 Introduction
1.1 Overview
This document captures the details of the Private Property Agency Feed Web Service API.
1.2 The Integration Process
Note: The most important prerequisite to integrating with Private Property is that the client
needs access to a programmer/developer competent in consuming XML web services.
The steps outlined below describe the process of setting up a new feed where there is no
existing connection to our systems.
1. Request for a feed is sent to Private Property via the Requester (a Private Property
Relationship/Account Manager).
2. Private Property Integrations Staff sends the API document through to the
Requestor.
3. The API document is sent by the requestor to the IT Provider elected to implement
their feeds.
4. The IT Provider sends a request to Private Property to set up a test branch on the
Private Property integration (sand box) server.
5. Private Property creates a test branch on the sand box server and the authentication
details are sent back to the IT Provider.
6. The IT Provider proceeds with the feed development.
7. The IT Provider tests the feed against the sand box environment. Private Property
Integrations staff will be present to assist with this process if required.
8. Private Property will test the completed feed integration and will notify the Requester
that the feed is ready to go live.
9. The Requester will give the go ahead to go live, after which Private Property will
create a branch on the live production site.
10. The credentials and live URL will be sent to the IT Provider to implement live.
11. Some warm-up testing on the live system will be carried out by Requestor, IT
Provider and Private Property Integrations staff and if all is well, the system will go
live.
Please note that this full process can take anything from 2 weeks to 2 months depending on
the experience level of the IT Provider and/or the complexity of the integration.

1.5 Getting Started
The first step it to initiate a request for a new feed. This can be done by sending a request
via the branch’s Private Property Account Manager, or by emailing the request through to
integration@privateproperty.co.za.
To help speed up the process, the following details are required:
• Name and contact details of the IT provider who is responsible for implementing the
feed for the agency.
• Name of agency requiring the feed.
• Name of Branch under agency requiring the feed.
• Email for the branch to which notifications will be delivered (it is advisable to use a
test email)
• Contact number for the branch
• Whether or not this branch is going to be sending through normal listings, FNB
Quicksell and or Nedbank Assisted Sale mandate types.
Once the branch has been correctly setup, the following details will be emailed to the
requester who must forward them on to the developer:
• User name
• Password
• GUID
The GUID is a unique identifier for the branch. The username and password are to be used
to build the token that is used for security authentication. Sample code to create the token is
available on request in the following languages: C#, PHP and Perl
The developer is then free to connect to the web service at the following URL and to start
calling the service methods.
https://services.sandbox.pp.co.za/AgentImport/AgentImport.asmx
A formal definition of each of the web-service calls services is available to developers on the
web-services page.
Please note that the Sandbox integration environment is only available during business
hours, from 06:00 until 19:00 GMT+2.

1.6 Moderation
Each listing that is uploaded via the web service goes through 2 levels of moderation in the
production system:
1. Automated moderation. Listings get declined automatically if they do not pass a
number of minimum criteria tests (see notes below). A notification email will go out to
the email setup on the branch describing the failed test.
2. Manual moderation. Once a listing passes automated moderation, it is activated
and may be reviewed by a member of a moderation team. You will be notified of the
listing activation.
Notes:
• For a list of minimum moderation criteria, please refer to Appendix B.
• On the sandbox system, listings ONLY go through automated moderation. Should
they pass they will be immediately activated and no manual moderation will be
applied.
• Once a listing has been activated in the sandbox environment, it may be viewed on
the sandbox portal at: https://www.sandbox.pp.co.za
1.7 Token Generation
A security token must be added to every soap call. It is a time based token that allows you
to access a specific data set until the token expires. Correctly manging the tokens allows
your calls to be secure and reduces the chance of others using your credentials to access
your clients data. You will need a single user name and password which will be applied to
all integrations that you do with Private Property for all your clients
To generate a token you will need:
Field Name Description
User name Your companies user name
Password Your Companies password
UID A unique code to make the digest
calculation unique
Expires The date and time until which this token is
valid*
Digest A base 64 encoded SHA1 hash
Stamp Time The time stamp at which the token was
generated
A token should appear as follows:
<Token>
<Digest>lxa4S/abJYHozy/rdm2i2WaSUvs=</Digest>
<UserName>youruser</UserName>
<StampTime>2016-04-26T00:04:33Z</StampTime>
<Expires>2016-04-27T00:04:33Z</Expires>
<UID>1738906</UID>
</Token>

1.7.1 Digest Generation
To generate a digest you will need to generate a string as follows:
UID + Stamp Time + Password + Expires
You will the need to create an SHA1 hash of that string. Finally you will need to Base 64
encode it so that it can be send in the XML document without errors
An example of the string to be hashed is as follows
17389062016-04-26T00:04:33Zmypassword2016-04-27T00:04:33Z
*Please note that because some servers do not update to be in sync the actual current time,
some servers might have a different time by a few minutes. You will need to allow for this in
the value of the Expires field

you forget to do this an exception will be thrown. A listing may have multiple
agents attached to it.
• Address can’t be altered after listing is activated
o Once a listing has been activated, the address details are locked down.
o This means that any requests to update the following address attributes will
have no effect:
▪ StreetName

o Furthermore, in such an update event, the above attribute changes will be
silently ignored, but all other attribute changes will be applied.
• Hiding of Address
o The system allows for the hiding of certain address details on the web site:
▪ Hide street name
▪ Hide street number
▪ Hide complex name
▪ Hide unit number
o This will prevent users from contacting the sellers directly and ensure security
for your mandates. If all of the above properties are set, only the suburb name
will display.
o An important point to take note of is that when any of the above properties are
set to true your listings will be negatively affected in the ranking of search
results. This means that your listings will not appear at the top of the search
results.
• Categories
o At least one category is compulsory: either ‘Residential’, ‘Land’, ‘Farms’ or
‘Commercial’.
o A listing may have multiple categories.
o Each category determines which mandatory attributes must be met, if the
mandatory attributes are not met then an exception will be thrown

• Photo Urls
o For Sales Listing Types, there is a minimum limit of 3 photos.
o For Rental Listing Types, there is a minimum limit of 3 photos.
o For any listing, there is a maximum limit of 256 photos. If more photo urls are
supplied, only the first 256 urls will be used.
o When updating a listing that is activated and there are no changes to the
images:
▪ You must include the namespace:
xmlns:xsi="http://www.w3.org/2001/XMLSchema-instance"
▪ You must include xsi:nil="true" on PhotoUrls
<PhotoUrls xsi:nil="true" />
o If the listing has been created but hasn’t been activated due to an error the
images must be supplied and will be validated.
Important: Avoid Unnecessary Image Re-Downloads
When you update an activated listing without changing the images, you must explicitly indicate that no
image updates are required. If you omit the xmlns:xsi namespace or fail to set <PhotoUrls xsi:nil="true" />,
our system will assume that you are sending a full image update. This triggers a forced re-download of
all images (as many as 256 high resolution images), even if they haven’t changed.
This results in significant and unnecessary bandwidth usage, increased processing load for both your
systems and ours, and - most visibly - a degraded user experience: every re-downloaded image must be
dynamically resized again, causing slow first-time load times for your listings on our platform.
Forgetting this step hurts your costs, our infrastructure, and your customers’ experience. Please
ensure these fields are correctly included in all update requests where images remain unchanged.
Recommended Integration Strategy
We strongly recommend that your system tracks image updates separately from normal listing updates. A
simple and effective approach is to maintain distinct timestamps, for example:
ListingUpdateDate: updated whenever any listing field changes
ListingImagesUpdateDate: updated only when image URLs change
PrivatePropertySyncDate: tracks when a listing was last successfully published to us
By comparing ListingImagesUpdateDate with the timestamp of your last successful sync, your system can
reliably determine whether image data actually changed. If it has not changed, you should:
Include namespace: xmlns:xsi="http://www.w3.org/2001/XMLSchema-instance"
Set nil attribute: <PhotoUrls xsi:nil="true" />
Image URLs: Avoid sending image URLs again - make sure that the collection is empty.
This ensures that only genuine image updates trigger a full image re-download on our side. Implementing
these timestamps will protect you from unnecessary bandwidth consumption, reduce processing load, and
ensure your listings load instantly for end-users.

o An Exclusive Listing receives the following features at no additional cost:
▪ Featured Listing Tile and Highest Ranking (up to a maximum of 7 days)

o Omission of this field, a nil value, or a value of zero will all be treated as if the

o Exclusive Listings must have a ListingType of Sale, for which the agency
holds a sole mandate.
o Valid values to enable the feature are 1–92 (days).
o A valid value represents the number of days from the listing's first submission

creation will result in an error. This is to prevent taking advantage of the alerts
and features and then retracting immediately.

5 Frequently Asked Questions
1 My listing comes back saying I’m not authorised to send through listings, why?
Ensure that the branch is setup correctly. To send through FNB Quicksell or Nedbank Assisted
Sale listings, the branch must be setup (enabled) to do this on private property’s management
system. To send through normal lists, a contract is required. On sandbox this is simulated.
2 My listing was sent through but is not on the sandbox site?
There are a number of reasons that this could have happened. If the branch is setup correctly,
a listing could be rejected or still waiting to be moderated. You can use the web service to get
the status of the listing.
3 My listing is still not showing and has a status “pending”
This means the listing is being moderated; there may be a backlog, the best thing to do would
be to wait a bit and try again later. If this process is taking too long, you should contact support.
4 My listing was rejected, why?
If your listing was rejected, there could be a number of reasons as to why it was rejected. Listings
are automatically tested for invalid data by our system; if it does not meet our criteria the listing
will be rejected. When rejected, a mail will go out to the branch email providing details of which
listing was rejected and why it was rejected.
5 My listing was rejected and I do not get reasons why it was rejected in a mail. Why?
Every time a listing is rejected through our automated tests, a mail will go out. IF you have not
received the mail, use the listing summary web service to see what mails were sent out and
ensure it is going to the correct email address. Note, that if a listing is rejected more than five
times, the system will block that listing from entering our system. Should there be a valid reason
for the listing being rejected, please contact our support centre.

There is an inherent order in which the methods on the web-services should be called. The
correct calling order will ensure that required entities exist on the system and do not cause
errors for dependant calls. For example, an agent cannot be assigned to a listing before that
