Metrics
Hot Chocolate provides several cost metrics used for execution limits and
billing calculations.
FieldCost
Estimated computational impact of executing a field on the server.
TypeCost
Estimated number of objects instantiated or returned by the query.
Note: Field and Type Cost follow the IBM cost specification:
https://ibm.github.io/graphql-specs/cost-spec.html#sec-Type-Counts
Complexity
Complexity = FieldCost + TypeCost
Complexity is used as a query limit / capacity control.
Example:
 If a client’s subscription allows 2000 complexity, then any query with
complexity ≤ 2000 is allowed.
 Queries exceeding this limit require the client to purchase additional
complexity allowance.
PriceSurcharge
An additional fixed credit amount applied to specific APIs or operations.
Example use cases:
 Report generation
 Bulk exports
 Heavy aggregation queries
CreditsConsumed
CreditsConsumed = FieldCost + TypeCost + PriceSurcharge
Credits are the billable unit consumed by each request.

Cancelling a Subscription
When a subscription is cancelled, any eligible unused subscription credits
from the current billing cycle are converted into prepaid credits.
This allows the remaining value of the current billing cycle to continue being
available on the account, while also ensuring that subscription-only benefits
do not continue after cancellation.
After cancellation:
 remaining subscription cycle credits are removed;
 eligible unused credits are converted into prepaid credits;
 the prepaid credits are added to the account’s prepaid balance;
 the account is moved to the default prepaid package;
 the account no longer has access to the subscription package’s
complexity limit or other subscription-only allowances.
How Remaining Credits Are Converted
The number of credits converted depends on two limits:
1. how many subscription credits are still available on the account; and
2. how much unused value remains in the current billing cycle.
The system uses the lower of these two amounts.
This prevents a client from receiving more prepaid credits than the unused
portion of the subscription represents.
Subscription Credits vs Prepaid Credits
Subscription credits and prepaid credits may have different conversion rates.
For example:

===== PAGE 8 =====
Credit Type Example Conversion Rate
Subscription credits 40 credits per cent
Prepaid credits 30 credits per cent
In this example, prepaid credits have a higher value per credit than
subscription credits.
Therefore, when remaining subscription credits are converted to prepaid
credits, the amount is adjusted using the prepaid conversion rate.
Example conversion ratio:
30 / 40 = 0.75
This means that every 1,000 eligible subscription credits would convert to 750
prepaid credits.
Example — Cancelling With Unused Credits Remaining
Assume the following:
Item Value
Remaining subscription credits 10,000
Unused prorated cycle value 8,000 credits
Subscription credit rate 40 credits per cent
Prepaid credit rate 30 credits per cent
The system first determines the eligible amount to convert.
Eligible credits = lower of 10,000 and 8,000
Eligible credits = 8,000
The system then applies the prepaid conversion ratio.
Prepaid conversion ratio = 30 / 40
Prepaid conversion ratio = 0.75
The prepaid credits granted are:
8,000 × 0.75 = 6,000 prepaid credits

Cancellation Audit
All subscription cancellations and credit conversions are recorded for audit
and support purposes.
The audit record includes the previous subscription credit balance, the
prepaid credits granted, the conversion rate used, and the relevant billing
cycle dates.
This allows both the client and support team to verify how the final prepaid
credit amount was calculated.
Default Prepaid Package After Cancellation
When a subscription is cancelled, the account is moved to the default prepaid
package.
The default prepaid package is a monthly package with a maximum query
complexity of:
MaxComplexity = 2,500
This means that after cancellation, the account may continue using any
available prepaid credit balance, but queries are still subject to the default
prepaid complexity limit.
If a query requires complexity greater than 2,500, it will not execute unless the
account purchases additional complexity allowance or moves to a package
with a higher complexity limit.
Example
Before cancellation, a subscription package may allow:
MaxComplexity = 3,000
After cancellation, the account is moved to the default prepaid package:
MaxComplexity = 2,500
A query with complexity 2,800 would therefore no longer execute after
cancellation, even if the account still has prepaid credits available.

Example 6 — Pagination Within Pagination
(Exponential Growth)

inside another paginated list, the number of returned objects can increase
rapidly.
This significantly increases TypeCost and FieldCost, which increases
CreditsConsumed.

Why Nested Pagination Increases Cost
According to the IBM GraphQL Cost Specification, TypeCost scales with the
number of returned objects.
When pagination occurs inside another paginated field, the total number of
instantiated objects grows multiplicatively.
Example:
suburbs(first:10)
properties(first:20)
owners(first:5)
Total possible returned objects:
10 × 20 × 5 = 1000
Each additional nested list multiplies the potential object count.
This is why deeply nested paginated queries can grow in cost very quickly.
Best Practices for Clients
To control cost and complexity:
• Avoid deeply nested paginated queries
• Use smaller first or last values
• Request only the fields required
• Use GraphQL-Cost: validate to estimate cost before executing queries
